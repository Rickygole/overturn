Overturn

Appeals that verify their own citations

Overturn turns a health insurance denial letter into a policy-cited appeal — checking every citation against the insurer's own published policy before a human ever reads the draft, and staying on the case for the weeks it takes a payer to answer.

The problem

A denial letter lands on a billing clerk's desk. Doing this properly means finding the insurer's own medical policy, checking the patient's chart against it criterion by criterion, and writing a letter that cites the policy back to them by section number.

That is a two-hour job, and there are forty other things to bill today. So most denials are never appealed — and a large share of the ones that are appealed get overturned, which means many of the claims nobody appealed were winnable. The bottleneck was never judgment. It is that the labour cost of one appeal exceeds the value of one claim.

What happens when a letter arrives

This is the demo, in order. Every line below is something the running system does.

  1. A letter lands in a bucket. Cloud Storage notifies Pub/Sub, which pushes to a private Cloud Run service. Nothing polls; the letter's arrival is what starts everything.
  2. Sentinel screens it before anything reads it. A denial letter is a document from an outside party, so it is treated as hostile. Three independent detectors: deterministic rules, Google Model Armor, and a Gemma pass. Any of them can halt the pipeline.
  3. Intake reads it. Payer, claim number, service denied, stated reason, appeal deadline. Every field is nullable — a null is recoverable, an invented claim number is not.
  4. Retrieval finds the rule they denied under. It returns the whole governing policy rather than the top-scoring fragments, because a criteria list truncated by rank has silent holes in it.
  5. Mapping does the real work. For each numbered criterion: does the chart document what the payer asked for? Each verdict carries a chart quote and a pointer to where it came from. This is a documentation question, never a clinical one.
  6. Drafting writes the appeal from the satisfied criteria only. It has no access to the policy corpus at all, so it cannot go looking for supporting material it was not given.
  7. Verification checks it three ways. Does every cited section exist — a set-membership test in Python, because a model cannot be wrong about a question it is never asked. Does the source text actually say what the letter claims. Does the letter assert any fact the chart does not support. Any failure sends it back with the specific reason. Three strikes and it goes to a person with nothing sent.
  8. Two humans sign. The clerk confirms the paper trail. The ordering clinician signs the clinical argument, on a separate screen. Neither alone transmits anything.
  9. Then nothing happens for weeks. No process runs. The entire state is one Firestore document. Cloud Scheduler wakes a job, finds cases past their payer deadline, and climbs the appeal ladder on its own — first level, peer-to-peer, second level, external review.

The moment that matters

On a real run against Gemini, Drafting overclaimed. It wrote that a 14 July 2026 encounter was a telehealth evaluation and named a provider the chart does not name. Nobody prompted this and nothing was injected — the model simply reached slightly past its evidence, which is exactly what these systems do.

Verification caught it.

drafting      attempt 1: 8 citation(s), 6 clinical assertion(s)
verification  attempt 1 REJECTED: 1 unsupported citation, 2 ungrounded assertions
              "The medical record does not mention that this evaluation was
               telehealth, nor does it identify 'Dr. Castellanos' as the provider."
drafting      attempt 2: 6 citation(s)
verification  attempt 2 REJECTED: 2 ungrounded assertion(s)
drafting      attempt 3: 6 citation(s)
verification  attempt 3 PASSED — awaiting human approval

A fault-injection switch exists to demonstrate the same loop deliberately. It is not what produced this. A safety net that has caught something real is worth more than one that has only ever been tested.

Does it actually get the right answer?

The failure worth worrying about is not a crash. It is a confident, well-cited, entirely irrelevant appeal — and nothing that asserts on status codes would notice one. So correctness is measured, against both a deterministic offline backend and real models, and both columns are published.

Architecture

What we found building it

Model Armor missed the injection

All four filters ran, EXECUTION_SUCCESS, NO_MATCH_FOUND. The deterministic rules layer caught it. Judged as a prompt the payload is unremarkable business correspondence; what makes it an attack is that a payer does not address a section to an automated claims agent.

Defence in depth is usually asserted and rarely demonstrated. This is why the consequence of a finding is decided in Python and not by whichever detector spoke last. The measurement.

Gemini 3.5 is global-endpoint only

Every regional endpoint returns 404 NOT_FOUND for gemini-3.5-flash while the Model Garden catalogue lists it GA. That reads exactly like the model not existing rather than like the wrong endpoint — and the contest requires 3.5 or newer, so it was a disqualification wearing the costume of a missing feature.

No Pro-tier model clears the floor

Every Gemini 3.x Pro identifier in the catalogue is preview and numbered below 3.5. So "use Pro for the hard call" became "use the newest GA Flash", and the reasoning was written down rather than quietly falling back to a 2.5 model that would have been disqualifying. Model choices.

The clerk is the wrong signatory

A billing clerk cannot competently judge whether "the chart documents that the contraindication was addressed" is fair. So the gate is two signatures: the clerk confirms the paper trail, the ordering clinician signs the medicine. Neither alone transmits.

Try it

git clone https://github.com/Rickygole/overturn.git
cd overturn && uv sync
uv run pytest -q                                    # 434 tests, a few seconds
uv run python scripts/run_pipeline.py CASE-001      # a clean case, end to end
uv run python scripts/run_pipeline.py CASE-002      # the poisoned letter
uv run python scripts/evaluate.py                   # the scorecard above

Nothing there needs a cloud project, an API key, or a network connection. The whole seven-agent pipeline runs offline and deterministically; only the generative calls are answered locally.
