This is one run, not a statistical claim. Real models are not deterministic, and re-running --live may move which cases land where. What is reliable across a re-run, because it is a property of the pipeline rather than of one sample, is the pattern: Verification catches specific, real overclaims, and nothing fabricated ever passed the grounding check.

The finding this page exists for

CASE-001 is the case the manifest calls easy — the chart plainly satisfies every criterion. Offline it drafts cleanly on the first attempt, because a scripted backend has no opinion of its own. Real gemini-3.7-flash did have one, and it was wrong in a specific, checkable way.

Attempt 1 asserted that the patient’s 14 July 2026 encounter was a telehealth evaluation. The chart records that encounter as an “interim review” and never says how it was conducted. Nobody prompted anyone to look for this. gemini-3.5-flash, running Verification, caught it:

The chart does not establish that the evaluation on July 14, 2026 was a telehealth evaluation, nor does it mention the timing of the request to establish it was within six months.

That finding, plus a second one about a device name the source text does not use, went back to Drafting as revision instructions. Attempt 2 dropped both claims and passed. The case reached the queue with a letter in which no clerk or clinician had to catch an overclaim — because Verification already had.

The same pattern recurred twice more in the same run, which is the reason to believe it is not one lucky sample. CASE-006 took three attempts: the first was rejected for requiring documentation the policy does not ask for, the second for reversing who said what — the letter attributed the patient’s own self-report to her supervisor. The third passed.

The cap holding, on a real model

CASE-007 is CASE-001’s chart delivered as a degraded fax transcript instead of clean text. Offline that difference is invisible. Live it was not: all three drafting attempts repeated the same “telehealth evaluation” overclaim that CASE-001 fixed in one revision, and none of the three corrected it against the noisier input.

The attempt cap was reached, Verification’s reasons were carried onto the case, and the case moved to needs_human_review with no appeal sent. The manifest expected an approvable letter, so this counts as one of the two misses — and it is the one worth reading. The honest description is not “the system got this wrong.” It is that a real model given a harder input produced a worse letter three times running, and the system refused to send it and asked a person instead. That is the failure mode this architecture is built to have.

CASE-006 is the other miss, and it is a judgment call rather than a defect. The manifest says the chart “probably” meets the criteria but does not document one of them. The real model read the same chart, and after two rounds of Verification correcting how it characterised the evidence — not whether evidence existed — judged that there was enough to argue, and produced a letter that passed. That is a real disagreement about documentation sufficiency between a scripted narrative and a model’s reading of the same chart. It is not a citation that does not exist and not a quote that does not resolve.

Mapping and Verification dominate the bill, not Drafting — even though Drafting is the one agent on the more expensive tier. Both are re-fed the full policy text and the full criteria matrix on every call, while Drafting only sees what has already been distilled. Cost tracks context size here more than model tier. Retrieval ran a model call for only four of the eight cases; the rest resolved deterministically.

The screening layer, measured

Sentinel claims three layers. Live, two of the three ran for real. The guard model (gemma-4-26b-a4b-it-maas) answered validly on all seven cases that reached it — CASE-002 never gets there, because the deterministic rule layer catches it first and quarantining is cheaper without paying a model to agree. Google Cloud Model Armor logged skipped_not_configured on every case: the capability is reachable on this project, but no template id is set in this environment. That is an honest state to report, not a working layer.

Getting Gemma working at all was a real fix, and it is worth naming because it is the kind of thing that quietly does not work. Bound to a response_schema, Gemini enforces the shape on the wire; Gemma does not. Asked for a full result object including fields the model never sees, it returned valid JSON containing one of them. Every run before the fix logged gemma:unavailable — a three-layer claim that was one layer in practice.

The test suite

437 tests, covering the negation and threshold logic in Mapping, the grounding checks in Verification, the idempotency guard under concurrent execution, the two-signature gate, the escalation ladder, and the screening rules. A test asserts that the count printed in the README matches the count actually collected, so this number cannot drift.
