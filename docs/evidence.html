What actually happened against a real model

Eight cases, two independent trials against real Gemini on Vertex AI, through two different backends. The interesting result is not the score. It is that the same model made the same unsupported claim both times, and the same check caught it both times.

The same overclaim, twice, on two different backends

The chart says “interim review.” Both first drafts said “telehealth evaluation.”

CASE-001 is the case the manifest calls easy. Offline it drafts cleanly on the first attempt, because a scripted backend has no opinion of its own. Real gemini-3.7-flash has one, and it is wrong in a specific, checkable way: the 14 July 2026 encounter is recorded in the chart as an interim review, and the chart never says how it was conducted. Nobody planted that overclaim, and nobody prompted anyone to look for it.

Trial 1 — 28 August 2026, Gen AI SDK direct

gemini-3.5-flash, running Verification with no ability to edit the letter it was judging, rejected drafting attempt 1:

The chart does not establish that the evaluation on July 14, 2026 was a telehealth evaluation, nor does it mention the timing of the request to establish it was within six months.

Verification rejecting CASE-001 attempt 1. Recorded in docs/EVALUATION.md, quoted verbatim from the case audit trail.

That finding, plus a second one about a device name the source text does not use, went back to Drafting as revision instructions. Attempt 2 dropped both claims and passed.

Trial 2 — the deployed fleet, on the ADK backend

A different day, a different code path into the same models, and no fault injected. Drafting attempt 1 asserted:

The patient had a telehealth evaluation with endocrinology on July 14, 2026, during which diabetes management was discussed in full.

CASE-001 drafting attempt 1, deployed fleet. Marked fatal / assertion_grounded by Verification.

Verification rejected it:

The medical record describes the encounter on July 14, 2026, as an ‘Interim review pending device authorisation’ and does not state or support that it was conducted via telehealth.

Verification rejecting CASE-001 attempt 1, deployed fleet. Readable in the draft history on the live case page — sign in and open CASE-001.

Why this is the result and not the score. One model catching one overclaim once is an anecdote. The same overclaim arising twice, from two different execution paths, on the case a test manifest calls the easy one — and being caught both times by an agent that can reject but cannot edit — is a reproducible failure mode with a reproducible detector in front of it. That is a claim about the architecture rather than about a lucky sample.

The pattern recurred elsewhere in the 28 August trial too. CASE-006 took three attempts: the first was rejected for requiring documentation the policy does not ask for, the second for reversing who said what — the letter attributed the patient’s own self-report to her supervisor. The third passed.

The cap holding, on a real model

In both trials, exactly one case exhausted the three-attempt limit and sent nothing. It was a different case each time.

In the 28 August trial it was CASE-007 — CASE-001’s chart delivered as a degraded fax transcript instead of clean text. Offline that difference is invisible. Live it was not: all three drafting attempts repeated the same “telehealth evaluation” overclaim that CASE-001 fixed in one revision, and none corrected it against the noisier input. In the deployed trial it was CASE-003, where the live queue records the reason plainly as “verification rejected all 3 drafting attempts.”

Either way the mechanism is identical: the attempt cap is reached, Verification’s reasons are carried onto the case, the case moves to needs_human_review, and no appeal is sent. The manifest expected an approvable letter in both instances, so each counts as a miss. It is the miss worth reading. The honest description is not “the system got this wrong.” It is that a real model produced a worse letter three times running, and the system refused to send it and asked a person instead. That is the failure mode this architecture is built to have.

The miss both trials share

CASE-006 is a judgment call rather than a defect, and it is the one case both trials got “wrong” in the same direction. The manifest says the chart “probably” meets the criteria but does not document one of them. Both real models read the same chart and — after Verification corrected how the evidence was characterised, not whether evidence existed — judged there was enough to argue, and produced a letter that passed. Two independent trials disagreeing with the manifest the same way is weak evidence that the manifest was right. It is not a citation that does not exist, and not a quote that does not resolve.

Mapping and Verification dominate the bill, not Drafting — even though Drafting is the one agent on the more expensive tier. Both are re-fed the full policy text and the full criteria matrix on every call, while Drafting only sees what has already been distilled. Cost tracks context size here more than model tier. Retrieval ran a model call for only four of the eight cases; the rest resolved deterministically.

The screening layer, measured

Sentinel claims three layers: deterministic rules, Google Cloud Model Armor, and Gemma as a guard model. In the deployment all three run. Every screened case in the live queue records its detectors as rules, model_armor:enabled, gemma — visible on any case page under “Detectors that ran.”

In the 28 August trial, run from a laptop, only two of the three ran: Model Armor logged skipped_not_configured on every case, because no template id was set in that environment. That was a configuration gap in one environment, not a missing code path, and it is reported that way in docs/EVALUATION.md rather than rounded up.

The guard model answered validly on all seven cases that reached it. CASE-002 never gets there: the deterministic rule layer catches the injected instruction first, and quarantining is cheaper without paying a model to agree.

Bound to a response_schema, Gemini enforces the shape on the wire; Gemma does not. Asked for a full result object including fields the model never sees, it returned valid JSON containing one of them. Every run before the fix logged gemma:unavailable — a three-layer claim that was one layer in practice.

The test suite

490 tests, covering the negation and threshold logic in Mapping, the grounding checks in Verification, the idempotency guard under concurrent execution, the two-signature gate, the escalation ladder, and the screening rules.

Some of them check this website. tests/test_docs_accuracy.py reads docs/*.html and fails the build if a page claims a provenance feature the schemas do not have, credits ADK with orchestration that agents/adk_fleet.py explicitly disclaims, names a Cloud Run service that infra/deploy.sh does not deploy, or prints a test count that has drifted from the README. Marketing copy is the easiest place in a project for a false claim to survive, so it is the one place here that is pinned by tests.
