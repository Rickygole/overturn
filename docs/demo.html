Three ways to watch it work

The deployed queue with real cases in it, a four-minute walkthrough, and a local run that needs no Google Cloud account and costs nothing.

1. The live review queue

This is the screen the clerk uses. It is the deployed system on Cloud Run, reading cases out of Firestore that were processed by the real agents on Vertex AI — not a mockup.

Sign in to the queue

Password northbeck-appeals-2026

The password exists so the queue is not open to crawlers, not to protect data. Everything behind it is synthetic.

Signing in lands you on the dashboard rather than a list: counts by who is waiting, the deadline pressure where there is any, and the closed cases listed rather than hidden — because a case that silently vanishes from a queue looks like a case that was lost. It reads 8 cases, 3 needing a person: two waiting on the clerk, one sent back, two with the payer, three closed.

All eight cases are loaded, in six distinct states. Three of those states are refusals.

CASE-006Escalated The seventh agent, doing its job unattended. Submitted, the payer went silent, the response window lapsed, and Lifecycle escalated it on its own from first_level_appeal to peer_to_peer_review. No human asked it to.
CASE-002Quarantined A denial letter with an injected instruction in it. Sentinel stopped it before any agent read it as instructions, so it never enters the queue as a review row. What it did.

CASE-008Declined — no basis A second denial on a still-undocumented record. Same refusal, arrived at independently.

Two things about that table that you should not have to find out later.

The clock is compressed. The deployment runs with OVERTURN_DEMO_TIME_ACCELERATION on, one second standing in for one day. It is a built-in setting, not a patch. A real payer response window is 30 days, and without compression nobody would ever watch an escalation happen. CASE-006’s escalation is real behaviour on a fast clock — the ladder, the trigger, and the audit entry are the production ones.

Nothing was transmitted to an insurer. “Submitted” means handed to services/payer_sim.py, a local simulator that makes no network calls at all. Northbeck Health Plan does not exist. No real payer, patient, or chart is involved anywhere in this system.

This is a second trial, not a copy of the evidence page. These cases were processed by the deployed fleet through the ADK backend. The eight-case run recorded in docs/EVALUATION.md was a separate trial on 28 August 2026 through a different code path. Both scored 6 of 8 against the test manifest, and they did not miss the same two cases: CASE-003 and CASE-007 swap places.

That is the useful part. Two runs of a non-deterministic model landing in different places is exactly what the evaluation says to expect. What did not move is the finding — on CASE-001 both trials produced the same unsupported “telehealth evaluation” claim, and Verification caught it both times. Both rejections, quoted side by side.

Every case page shows the original letter, the screening result with the detectors that ran, the criteria matrix with each verdict and its chart locator, the full draft-and-rejection history, and the two-signature gate. Nothing can be submitted without both signatures on the same draft attempt.

3. Run the whole thing yourself

The pipeline ships with a scripted backend that answers every model call deterministically. All eight cases run end to end with no Google Cloud project, no credentials, and no cost — the same agents, the same orchestration, the same grounding checks. Only the model responses are canned.

git clone https://github.com/rickygole/overturn
cd overturn
uv sync

# all eight cases, offline and free
uv run python scripts/evaluate.py

# one case, with the full audit trail printed
uv run python scripts/casectl.py run CASE-001 --explain

# the approval queue on localhost
uv run uvicorn services.approval_ui.main:app --port 8080

To point the same run at real Gemini on Vertex AI instead, set two variables. This is exactly how the numbers on the evidence page were produced:

OVERTURN_RUNTIME_MODE=local OVERTURN_LLM_BACKEND=vertex \
    uv run python scripts/evaluate.py --live

The offline and live runs are the same code path. Only the backend is swapped. That is what makes the two scorecards on the evidence page comparable — and it is why the two cases where they disagree are worth reading rather than hiding.
